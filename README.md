# NovaChat

NovaChat is a full-stack AI chat application with persistent conversations, session-based accounts, long-conversation context management, and retrieval-augmented generation (RAG) over documents uploaded to a chat thread. The frontend is built with React and Vite; the backend uses Express, Passport, and MongoDB. Gemini generates chat responses and document summaries, while document embeddings are generated locally.

## Features

### AI chat and conversation management

- **Streaming responses:** The backend requests a streaming completion and forwards assistant text to the browser as Server-Sent Events (SSE). The chat UI reads the stream and updates the in-progress assistant message as content arrives.
- **Persistent threads:** User and assistant messages are stored in MongoDB. A new thread is created on the first message, with its title derived from that message.
- **Thread history:** The sidebar lists a user's threads by most recently updated, loads a selected thread's messages, starts a new thread, and deletes a thread.
- **Markdown rendering:** Assistant messages are rendered as Markdown, with syntax highlighting for code blocks.
- **Conversation context management:** The chat controller keeps recent messages in the model prompt. When enough unsummarized history accumulates, it asks the model to merge an older batch into a concise, persistent summary, then supplies that summary alongside recent messages on later requests.

### Document RAG

- **Thread-level uploads:** The chat UI accepts PDF and TXT files. The upload endpoint extracts PDF text with `pdf-parse` and decodes non-PDF uploads as UTF-8 text.
- **Document summaries:** During ingestion, Gemini summarizes an initial excerpt of the extracted text into a short description stored with the thread's document metadata.
- **Local embeddings:** Text is split into overlapping chunks. `@huggingface/transformers` runs the `Xenova/all-MiniLM-L6-v2` feature-extraction model locally to create normalized embeddings; document text embeddings are not generated by a hosted embedding API.
- **MongoDB-backed vector data:** Each chunk is stored with its content, embedding, filename, owner, and thread ID.
- **Similarity retrieval:** For a chat in a thread containing documents, the backend embeds the latest query, computes cosine similarity against that thread's stored chunk embeddings, and adds the top matching chunks to the model context.
- **Grounded-answer instructions:** Retrieved text is sent to Gemini with instructions to use it when relevant, cite source filenames, and distinguish answers not supported by the supplied context.
- **Document cleanup on thread deletion:** Deleting a thread also removes its associated document chunks.

### Authentication and access control

- **Passport local authentication:** Users can sign up, log in, check their session, and log out. `passport-local-mongoose` integrates local credentials with the user model.
- **Server-side sessions:** Express Session and Passport maintain browser sessions using an HTTP-only cookie.
- **Owner-scoped data access:** Chat routes require authentication. Thread queries and document retrieval are scoped to the authenticated user's ID; retrieval is additionally scoped to the current thread.
- **Protected frontend route:** The chat page checks the backend session before rendering and redirects unauthenticated users to the authentication page.

## How It Works

### Chat request lifecycle

1. The frontend sends a message and thread ID to `POST /api/chat` with the session cookie.
2. The backend verifies the authenticated user, loads or creates the user's thread, and saves the incoming message.
3. The controller assembles the model context from the stored conversation summary and recent messages. If the thread has documents, it also embeds the latest query and retrieves up to three matching chunks.
4. The backend streams the model's response as SSE events. The frontend parses the events and appends content to the visible assistant message.
5. After generation completes, the assistant message and thread update time are saved in MongoDB.

### Long-conversation context

The controller keeps a recent message window of up to 10 messages. Once at least 10 messages are not yet covered by the stored summary, it summarizes the next batch of four messages together with the existing summary. The updated summary is persisted on the thread and supplied as earlier-conversation context on future requests. If summarization fails, the chat request continues with the existing summary and available recent messages.

### Document ingestion and retrieval

1. An authenticated user uploads a PDF or TXT file from within a chat thread.
2. The backend extracts text, asks Gemini for a concise topic-and-scope summary, and splits the extracted text into chunks of about 800 characters with 150 characters of overlap.
3. Chunks longer than 50 characters are embedded locally and saved as `DocumentChunk` records associated with the user and thread.
4. On subsequent messages in a thread marked as containing documents, the backend embeds the latest query and scores that thread's chunks using cosine similarity.
5. Up to three chunks are added to the system context before the chat messages, along with instructions to cite filenames and be transparent when the context does not contain an answer.

Retrieval currently runs for **every chat message in a thread with documents**; the application does not yet classify whether a question needs RAG or decompose complex questions into subqueries. The current controller passes a minimum similarity score of `0.0`, so the top-three limit is more selective than the score cutoff. Similarity filtering and query-aware retrieval tuning remain areas for improvement.

## Requirements

- Node.js 20.19+ or 22.12+ (Vite 8 requirement).
- npm.
- A MongoDB instance, local or hosted.
- A Gemini API key for chat responses and document summaries.

The first local embedding request may take longer while the Transformers.js model is downloaded and initialized.

## Configuration

Create `Backend/.env`:

```env
LOCAL_MONGODB_URI=mongodb://127.0.0.1:27017/novachat
GEMINI_API_KEY=your_gemini_api_key
SESSION_SECRET=replace_with_a_long_random_secret
```

`SESSION_SECRET` has a development fallback in the server, but set a unique secret in every deployed environment. Keep `.env` out of version control and never commit API keys or database credentials.

The chat controller currently selects Gemini. `Backend/utils/llmServe.js` also defines configurations for Groq, NVIDIA, and OpenRouter, but those providers are not selected by the current chat flow.

## Installation and Local Development

Install dependencies in separate backend and frontend directories:

```bash
cd Backend
npm install

cd ../Frontend
npm install
```

Start MongoDB and configure `Backend/.env`. Then start the backend in one terminal:

```bash
cd Backend
npm run dev
```

The backend listens on `http://localhost:8080` and uses Node's watch mode for development. Start the frontend in another terminal:

```bash
cd Frontend
npm run dev
```

Vite serves the frontend at `http://localhost:5173`.

Frontend checks:

```bash
cd Frontend
npm run lint
npm run build
```

## API Reference

Authentication and document routes are mounted outside the `/api` prefix. Protected endpoints require the session cookie established by login or signup.

### Authentication

| Method | Endpoint | Description |
| --- | --- | --- |
| `POST` | `/auth/signup` | Create a local account and log in. Expects `username`, `email`, and `password`. |
| `POST` | `/auth/login` | Authenticate with local credentials and establish a session. |
| `GET` | `/auth/session` | Return the current authenticated user, or `401` if there is no session. |
| `GET` | `/auth/logout` | End the current Passport session. |

### Chat and threads

All endpoints in this table are under `/api` and require authentication.

| Method | Endpoint | Description |
| --- | --- | --- |
| `GET` | `/thread` | List the current user's threads, newest updated first. |
| `GET` | `/thread/:threadId` | Load the messages for an owned thread. |
| `POST` | `/chat` | Save a user message, generate and stream a response, then persist the assistant message. |
| `DELETE` | `/thread/:threadId` | Delete an owned thread and its document chunks. |

Chat request body:

```json
{
  "threadId": "client-generated-thread-id",
  "message": "Summarize the main findings in my report"
}
```

`POST /api/chat` returns `text/event-stream`, not a JSON `{ "reply": "..." }` object. Content events have JSON data with a `content` field; the stream ends with a `done` event. If generation fails after streaming starts, the backend sends an `error` event.

### Documents

| Method | Endpoint | Description |
| --- | --- | --- |
| `POST` | `/document/upload` | Upload a file as multipart form data with fields `file` and `threadId`; extracts text, summarizes it, chunks it, and stores local embeddings. |

The upload route requires authentication and an existing thread owned by the current user. The frontend file picker advertises `.pdf` and `.txt` files.

## Security and Deployment Notes

- Chat and document routes use Passport's authenticated session, and thread operations include an owner filter.
- Chunk retrieval filters by both owner and thread, preventing a thread from retrieving another user's or another thread's chunks.
- The session cookie is HTTP-only. The current development configuration sets `secure: false`; production should use HTTPS, secure cookies, and an appropriately configured proxy/session store.
- CORS currently allows `http://localhost:5173`, and frontend API calls use the fixed `http://localhost:8080` origin. Update these for deployment and use environment-based configuration before exposing the app publicly.
- The upload route uses in-memory Multer storage and currently has no explicit file-size limit or server-side file-type allowlist. Add both before accepting untrusted production uploads.

## Current Limitations and Next Steps

- Complex-query decomposition and per-subquery retrieval are planned, not implemented. Current RAG embeds the entire latest message once.
- The backend retrieves chunks whenever a thread has documents; it does not first decide whether the question is document-related.
- Retrieval scans the thread's stored chunks in application code instead of using a vector database or indexed vector search. This is suitable for a prototype but scales linearly with the number of chunks in a thread.
- The minimum similarity passed by the chat controller is `0.0`; tune this threshold against representative questions to avoid adding weakly related context.
- Scanned PDFs require OCR, which is not currently included.
- The system prompt asks the model to cite filenames, but citations are free-form generated text rather than validated citation objects.
- Add ingestion limits, server-side file validation, retrieval evaluation cases, and robust document deletion/re-indexing as the RAG feature matures.
